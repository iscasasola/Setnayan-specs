Vendors V1 — manual encoding, payment-deadline tracking

Couple-managed registry of every external supplier. Hybrid taxonomy (28 canonical services + custom rows), flexible payment milestones, computed crew meal totals, R2-stored contracts. No vendor app, no wallet integration — vendor money is external to Setnayan.

Key design decisions

Hybrid service taxonomy

28 canonical services as the spine — drives gap-checking and Budget rollup. Couples can add custom rows for the long tail (late-night ulam stations, processional choirs, bibingka carts) without polluting the canonical list.

Flexible custom milestones

Any number of payment milestones per vendor with custom labels and due dates. Presets scaffold "Reservation + Down + Balance" and "4 partials + Balance" patterns without locking the schema.

Crew meals computed

Count × per-meal cost = total, with a "vendor provides meals" toggle that zeroes out without losing headcount. Rolls up to event-level estimate; feeds 0007 Budget as a single row.

No wallet integration

Vendor payments leave Setnayan — cash, GCash, bank transfer, direct to vendor. Wallet (0003) is reserved for Setnayan SKUs. Recording, not processing. Combined views can live in Budget (0007) without coupling the two.

Manual encoding only

No vendor login, no vendor self-input. Din (Phase 3 supplier app) inherits these records later with no migration. Building a half-baked vendor surface in V1 would block launch.

PHP-primary, no tokens

Vendor money never touches Setnayan's books — no reason to render in tokens. Tokens stay in Setnayan's own paid surfaces (Pro widgets, Papic, Templates, Monogram, Panood, LED).

Meetings live in vendor profiles

Multiple meetings per vendor (initial consult, tasting, walkthrough, fitting, etc.) with title, datetime, mode (in-person / video / phone), location/link, agenda, attendees, notes. Soonest one surfaces as "Next meeting" on the vendor card. Couple-encoded in V1; created_by_actor column lets Din (Phase 3) write vendor-originated rows into the same table without migration.

28 canonical services

Code-shipped enum, ordered roughly by planning priority. Couples select which apply, mark unwanted ones as "not needed," and add custom rows for niche needs.

ceremony_venue · reception_venue · catering · photography · videography · same_day_edit · drone · prenup_shoot · wedding_coordination · hmua · bridal_gown · groom_suit · entourage_attire · florals · cake_desserts · lights_sound · dj_emcee_host · mobile_bar · live_band · acoustic_performer · choir_string_quartet · officiant · transportation_bridal_car · transportation_guest_shuttle · invitation_print · stationery_signage · photobooth · souvenirs_giveaways · wedding_rings · honeymoon_planner

Connection to other iterations

Depends on (< 0006): 0001 (event scaffolding, dashboard shell, file upload primitive). Independent of 0002–0005.

Provides to (> 0006):

  • 0007 Budget & Expenses — every booked vendor becomes a budget row; payment milestones populate the cash-flow timeline; crew meal aggregate is a single budget line.
  • 0010 Mood Board — styling vendors (florist, lights & sound, future stylist) link to mood board segments.
  • Phase 3 Din — supplier app inherits these vendor rows; no migration required.

Acceptance criteria

Couple can add a vendor with manually entered identity fields
Hybrid service assignment: multi-select 28 canonical + add custom inline
Mark canonical service "not needed"; gap count updates
Package: name + total in PHP centavos + free-form inclusions list
Any number of payment milestones per vendor with label / due date / amount
Mark paid records date, amount, method, reference; balance auto-updates
Overdue milestones surface in red on list and detail views
Crew block: count × per-meal cost = computed total; rolls up to event level
"Vendor provides own meals" toggle zeroes that vendor's contribution
Contract upload (PDF/JPG/PNG, ≤25 MB) lands in R2 PH bucket
Service coverage view shows all 28 canonical services with status + vendor
Stats strip aggregates contracted, paid, outstanding, next deadline, crew meals, coverage %
All currency in PHP-primary format (₱ symbol; no tokens anywhere)
Mobile view: thumb-friendly, ≥44pt taps, single-column cards, FAB for add-vendor
Vendor status workflow lead → booked → completed → cancelled (any direction)
5-year R2 retention on contracts; metadata kept after file expiry
Multiple meetings per vendor: title, datetime, mode, location/link, agenda, attendees, notes
"Next meeting" surfaces the soonest upcoming on each vendor card
Past-but-still-scheduled meetings render amber and prompt confirmation
created_by_actor column ready for Din vendor writes (no migration needed)
