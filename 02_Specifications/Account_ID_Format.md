# Account & Entity ID Format — Setnayan canonical reference

**Status:** Locked 2026-05-12
**Applies to:** Every customer-facing identifier across the platform.
**Replaces:** Earlier `STNYN-XXXXXXXX` reference codes documented in iteration 0034 § 4.1 (those were superseded by `SET-XXXXXXXX` during the rename cleanup; this doc supersedes BOTH and locks `S89O-` for orders).

---

## 1. Format

```
S89<TYPE>-<10-char body>
```

- **`S89`** — fixed brand prefix. Three characters, always uppercase. Pronounced "ess-eight-nine."
- **`<TYPE>`** — one uppercase letter denoting the entity type. See § 2.
- **`-`** — literal dash separator. Visual delimiter; not stored in DB.
- **`<10-char body>`** — 10 characters drawn from Crockford base 32 (`0-9` + `A-Z` minus `I`, `L`, `O`, `U` — removes the easily-mistyped chars). 32^10 = 1.13 quadrillion possible values per type.

**Note on base 62 vs Crockford base 32.** The original direction was "alphanumeric base 62." Recommending Crockford base 32 instead for two operational reasons: (a) all-uppercase reads cleaner over the phone for support calls, and (b) the omitted ambiguous characters (`I` / `1`, `L` / `1`, `O` / `0`, `U`) prevent the most common human-transcription errors. If you'd prefer full base 62 mixed case for tighter density, flip one line in the SQL generator function — the spec carries both options. Crockford is the default.

Example IDs:

```
S89U-A4F2K9R7BX     (a user)
S89V-K7N3X9P2VW     (a vendor)
S89E-9F8M2K7N3X     (an event)
S89O-B2N7K9R3X4     (an order)
```

Reading guide: visually scan the type letter (4th position) to know what kind of row you're looking at; the body after the dash is opaque random.

## 2. Type letters

| Letter | Entity | Table | Notes |
|---|---|---|---|
| `U` | User (any account) | `users` | Covers customers, vendors, admins, guests. Every login has one. |
| `V` | Vendor (business) | `vendors` | A vendor account has BOTH a `S89U-` (its login user) and a `S89V-` (its public business profile). |
| `E` | Event | `events` | Weddings in V1; the per-event identifier the couple shares. |
| `O` | Order | `service_orders` | In-app SKU purchases. Replaces the prior `SET-XXXXXXXX` reference-code prefix from iteration 0034. |

**Type letters NOT used in V1 (reserved for future):**

| Letter | Reserved for |
|---|---|
| `A` | Admin-action audit IDs |
| `B` | Bookings (vendor reservations made through the marketplace) |
| `C` | Contracts (iteration 0032) |
| `G` | Guest invitation tokens |
| `M` | Messages / threads (iteration 0019) |
| `P` | Payments (sub-entities of orders) |
| `S` | Saved seating-chart layouts |
| `T` | Tickets (support — iteration 0029) |
| `R` | Refunds |

If a new entity type lands in V1.5 and needs a customer-facing ID, pick from this list rather than inventing a new letter.

## 3. Generation

**Randomness, not increment.** IDs are generated by drawing 10 characters uniformly from the Crockford alphabet at insert time. The DB does a uniqueness check inside the same transaction; on collision (vanishingly rare at 32^10 search space), it retries.

**Internal `bigserial` stays.** Every table also has a hidden `id bigserial PRIMARY KEY` used for joins, indexing, and foreign keys. The `public_id` column is what shows up to customers, on receipts, in QR codes, in support transcripts. Internal joins NEVER use the public_id.

### Postgres function

```sql
CREATE OR REPLACE FUNCTION generate_public_id(type_letter CHAR(1))
RETURNS TEXT LANGUAGE plpgsql AS $$
DECLARE
  alphabet TEXT := '0123456789ABCDEFGHJKMNPQRSTVWXYZ';  -- Crockford base 32
  body TEXT := '';
  i INT;
BEGIN
  FOR i IN 1..10 LOOP
    body := body || substr(alphabet, 1 + (random() * 31)::INT, 1);
  END LOOP;
  RETURN 'S89' || upper(type_letter) || '-' || body;
END;
$$;
```

Tables call it as a `DEFAULT`:

```sql
ALTER TABLE users
  ADD COLUMN public_id TEXT NOT NULL UNIQUE
  DEFAULT generate_public_id('U');
```

Collision retry is delegated to the `UNIQUE` constraint plus the standard `INSERT ... ON CONFLICT DO NOTHING RETURNING` pattern in application code.

## 4. Display & input

### In customer-facing surfaces

- Always show the full `S89X-XXXXXXXXXX` form. Don't truncate.
- Render in `font-family: ui-monospace, SF Mono, Menlo, monospace` for legibility.
- Letter-spacing `0.04em` is comfortable; the prefix and body should read as two distinct chunks.

### In admin / support contexts

- Display as-is. Admins memorize the type letters quickly.
- Search inputs accept either the full ID or just the 10-char body (server appends the prefix back during the lookup if missing).

### In QR codes

- Encode the full ID. QR readers handle the dash fine.
- For deep-links combining an event + a guest (e.g. RSVP scan), the URL pattern is `setnayan.com/e/{S89E-…}/g/{S89U-…}` — both segments visible.

### Case sensitivity

- IDs are **case-insensitive on input** (we lowercase the body and re-uppercase before lookup), **uppercase on storage and display**.
- Crockford normalization: input `o` → `0`, input `i` or `l` → `1`, input `u` → strip (treated as a typo). These are all impossible characters in our alphabet anyway.

## 5. Migration from prior conventions

Two previous ID conventions exist in the spec history:

1. **`STNYN-XXXXXXXX`** (iteration 0034 original) — STNYN was the consonant-only wordmark, retired 2026-05-12. The cleanup pass on the same day flipped this prefix to `SET-XXXXXXXX` as an interim.
2. **`SET-XXXXXXXX`** (rename-cleanup interim) — superseded by this document. Order public IDs are now `S89O-XXXXXXXXXX`.

**Action items for iteration 0034:**

- `service_orders.reference_code` column rename → `public_id`.
- Length spec: change from "8-char base32" to "10-char Crockford base 32" (slight density increase; collision-resistant).
- Generation function: use the canonical `generate_public_id('O')`.
- Customer-display format: `S89O-XXXXXXXXXX`.

The `payment_inbox_messages` reconciliation matcher (iteration 0034 § 11) needs its regex updated:

```
OLD:  reference_code ~ '^(SET-|STNYN-)?[0-9A-Z]{8}$'
NEW:  reference_code ~ '^(S89O-)[0-9A-HJKMNP-Z]{10}$'
```

## 6. Constraints & invariants

- **Format is content-free.** The body never encodes anything (no embedded type-letter inside the body, no encoded timestamp, no encoded sequence). All metadata lives in the row itself.
- **One canonical type per table.** A user only ever has a `S89U-` ID. A vendor account has both `S89U-` (login) and `S89V-` (business profile), stored in different tables.
- **IDs are never reused** across deleted rows. Soft-delete preserves the public_id; hard-delete (rare, RA 10173 "right to erasure") tombstones the row but does not release the ID for reuse.
- **No ID enumeration through any public API.** Listing endpoints return only IDs the caller is authorized to see; iteration 0033 (Public API Foundation) enforces this via scoped tokens.

## 7. FAQ

**Why a fixed `S89` prefix?** It identifies the platform at a glance even out of context. A customer sees `S89O-…` on a payment confirmation email forwarded to their accountant and the accountant knows it's a Setnayan order.

**Why not sequential?** Sequential IDs let attackers enumerate the user base (try `S89U-0000000001`, `…0000000002`, etc.). Random 10-char Crockford bodies prevent that.

**Why 10 characters?** Collision resistance with comfortable margin. 32^10 = 1.13 quadrillion. If Setnayan signs up 1 million users, the probability of collision on the next insert is ~1 in a trillion. Plenty of headroom.

**Why Crockford base 32 over base 62?** Phone-call legibility. "S-89-U-dash-Alpha-4-Foxtrot-2-Kilo-9-Romeo-7-Bravo-X" — every character is unambiguous over voice. With mixed-case base 62 you'd be saying "uppercase A" / "lowercase a" constantly.

**Can the prefix be removed?** Yes, easily — drop the `'S89' ||` from `generate_public_id` and you have a 12-char ID. The brand prefix is a stylistic choice, not a security or correctness mechanism.
