# Suppliers page — check before design · 2026-10-07 (Fable)

**Owner's brief, verbatim (2026-10-07):** *"right now you have hidden the bench the compare budget, and everything else in the suppliers and just showed suppliers that are booked. we want to create a uni screen interface that adapts to both desktop and mobile view. which handles everything we have and still keeps it un clumped. i want a uniscreen that can help them navigate properly to all their categories, find suppliers, compare combinations, add supplier manually, chat with suppliers, and still make it look legible to the eyes. with animation"*

**Owner, later still (2026-10-07), on the six-section version, verbatim:** *"Looking at it feels so many things to do, unlike in event hub maker, there is a lot but my brain can manage to know where to go and what to do."* · *"when you click add to build a small pop up showing our build (like a shopping cart pop up)"* · the build verbs: *"view this build, save this build, compare to other build, view all builds?"* · on the Date & place section: *"this is already found inside the date and location on top."* ⇒ the prototype takes the **Maker's shape**: one segmented control (Find · Build · Booked, like Stages | Studio), one full-width body showing one thing, the tool at the thumb (the build pill; the category dropdown was retired once the open category pins), and a cart that peeks on Add to build. On a phone the visible "Suppliers" title row is dropped (owner 2026-10-07: *"should we remove this row?"* — the bottom bar names the page, the Maker has no title row; the h1 stays for screen readers and on desktop). The control is the shipped `ISegmented` (tone wine), pinned under the shell bar with the date · place line as you scroll (owner: *"this will stay prominent when scrolled up?"*); an open category's header pins under that block so it can be collapsed from deep in its list (owner: *"category pins if they are searching on that category so they can collapse"*), and the face is the Maker's, Hanken Grotesk (owner: *"make the design universal"*, *"follow the font used on the event hub maker"*). Date · place is the line under the title only; its ladders live inside what it opens.

**Owner, later the same day, verbatim — the journey the page must follow:** *"1. they start looking for categories and search or add manually their suppliers · 2. they get to talk and inquire services · 3. they accept their price proposal · 4. the can start creating builds. to compare combinations of each vendor they get · 5. compare multipl builds · 6. book a supplier's service · 7. see all booked services · 8. see the budget on where they are · 9. see if the date becomes more specific. and location also becomes more specific."* And: *"once they have locked vendors. this data can be used across the event."*

**How this was measured.** The live site (`www.setnayan.com`) at 375 px, signed in on the owner's event (looked only; nothing pressed except the "Saved" row, which only scrolls), plus `origin/main` at `fe86472846` read from a detached worktree. Anchors are file:symbol, never line numbers. Screenshots: `prototypes/suppliers_page_live_2026-10-07-*.jpg`.

## Verdict

**The complaint is accurate, and the cause is one CSS class.** The page opens to the booked rows and a five-row menu. Everything else — the bench, Picks, the six money figures, Plans, Payments — sits in one `#team-find-area` that is `hidden lg:block` and is not even mounted on a phone until a menu row is tapped (`services-takeover.tsx:ServicesTakeover`). When it does open it is one tall scroll, with Payments and Your plans collapsed at the very bottom. Three jobs leave the page entirely: **Find a supplier** (`/vendors/categories`), **Budget** (`?part=budget`) and **Chats** (`/messages`). On a computer it is the same phone column plus a 380 px rail. No design in the corpus draws a one-screen page; the nearest approved pieces are listed below and the prototype assembles them.

## Button colours — one colour per meaning (owner 2026-10-07: *"color code each button so they can have easier familiarity with the colors. base it on the recommended colors for that button across the internet"*)

The web's shared convention is not per-button, it is per **meaning** — the semantic set every major system ships (Bootstrap `primary / success / info / warning / danger`, Material and Ant's equivalents, Apple's red for destructive). So each button takes the colour of what it does, and the same meaning is the same colour on every screen:

| Colour | Meaning (the convention) | Buttons on this page |
|---|---|---|
| **Terracotta** (the CTA token — still *named* `mulberry` in `globals.css`: #C24E25 light · #E5794E dark; `ISegmented tone=wine` fills with it) | primary — the forward step you most want | **Find** segment · **Add to build** · Save this build |
| **Green** (`--ok`) | success / confirm / money committed | **Book** · Book this build · Pay · Record payment · Paid in full · In your build ✓ |
| **Blue** (`--info`) | messaging / information | **Chat** · Ask for a quote · Read their reply · Open full chat |
| **Amber** (`--warn`) | attention, something waiting on you | **Nudge** · Ask about another day (date conflict) |
| **Red** (`--danger`) | destructive — take it back | **Remove** · Cancel booking |
| **Grey** (ink/mute) | neutral — manage, edit | Your record · Set price · Workspace |

Main verb = filled with its colour; the rest = outlined, colour ink + a 9 % tint. ⚠ The first cut of this used the retired Rich Mulberry #5C2542 with an invented pink dark twin (#B8889C) — owner: *"why pink?"* — fixed to the shipped token; never derive a brand colour from memory, read `globals.css`. Every colour has a dark-mode twin (lighter, with dark ink on a filled button). Proof: `prototypes/suppliers_page_2026-10-07_fable-14-button-colours-light.jpg` / `-15-…-dark.jpg`.
⚠ Book and Pay share green deliberately — both are "commit"; their icons (calendar-check vs card) and words tell them apart. If the owner wants Pay distinct, the only honest alternative is the brand colour (PayPal/GCash/Maya each use their own brand for Pay — there is no cross-site standard).

### The handshake protects the booking fee — owner rule, 2026-10-07 (NOT what ships today; measured on the owner's own live page)
Owner, verbatim: *"no handshake, no record. no handshake, no access to certain features. no handshake, no confirmation of the event being booked to them"* · *"meaning. no booking fee paid to us."* · *"having multiple events that did not complete booking fee but were booked can be flagged"* · *"detect if they have a user creating an independent budget that is similar to their agreed price."*

**What ships today (why this is a change, not a description):** the owner's live Suppliers page shows two self-added suppliers as **Booked** with **Pay ›** and no handshake — `finalizeVendor` locks off-platform suppliers directly (44 of 45 prod bookings); `recordDeposit` is *pay first, then record* (S19) — a payment can be recorded before the yes; for marketplace suppliers the handshake exists behind `NEXT_PUBLIC_LOCK_HANDSHAKE_ENABLED` (`lib/lock-handshake-flag.ts`; a test comment says prod read "true" once — unverified today).

**The rule already exists — cite it, do not re-invent it (owner: *"we already have this rule"*):** `DECISION_LOG.md` 2026-09-20 *"THE BOOKING FEE UNLOCKS THE EVENT — three stages per (shop × event)"*, re-confirmed 2026-09-22, and **ON in production** since 2026-09-22 (`platform_settings.fee_unlocks_event_enforced = true`, read through `resolveFeeEnforcement`). The mechanism is one pure function, `eventAccessUnlocked({ charge })` in `apps/web/lib/event-access-stage.ts`, reading `booking_fee_charges` per event vendor: `paid` · `waived_free5` · `waived_import` unlock; `pending` · `failed` · `expired` lock. Nine supplier-side surfaces already call it (customer card + tabs, production sheet, seat plan, mood board, live/Papic). What the fee unlocks for the supplier is the owner's seven-item list of 2026-09-20 (full details · feature requests · Papic · Event Hub · portfolio · story · "whatever should only work after the fee").
**The exceptions, as they ship (owner: *"there are exceptions of booking fee as well"*) — all three are "settled" to `eventAccessUnlocked`, so none of them ever shows "Waiting for their yes" once the supplier has agreed:** `waived_free5` — a supplier's first five bookings (the launch waiver; the single most load-bearing member of the allowlist) · `waived_import` — a booking the supplier brought themselves (`host_manual` · `invite_claim` · `degree` · `website` inquiry sources, `lib/booking-fee-gate.ts`) · `waived_promo` — an admin free-fee window (2026-09-22) (there is no `waived_couple` — the only hit is a test asserting that no couple-facing notification sibling exists). A waived charge still mints a `booking_fee_charges` row (no `orders` row) and still sends the supplier a receipt email (2026-09-20). **Owner 2026-10-07, verbatim: *"these exceptions considers them as a completed handshake as well. only difference is they have to buy to get papic credits to take photos, and papic challenge is separate, and 3d plan."*** — so a waived supplier gets everything the fee unlocks; what the fee never includes, paid or waived, is **Papic credits** (suppliers shoot from their own credits — 2026-09-22), the **Papic challenge**, and the **3D plan** — those stay separate purchases. The page's Waiting state therefore keys on the charge's **settled-or-not**, never on "paid" — reading it as paid alone would lock every supplier out of their first five bookings.

**What THIS page adds is only the couple's side of the same charge:** the Suppliers page reads the same `booking_fee_charges` status for each supplier row, and while it is not settled the couple sees "Waiting for their yes" with nothing open — the mirror of `event-locked-by-fee.tsx` on the supplier side. And the leak check below exists to protect **`waived_import`**: a sourced booking re-entered as "my own supplier" would be waived as an import — that is the bypass the owner is closing.

**The design (in the prototype, corpus this date):**
1. **Book = ask.** A marketplace supplier goes to **Asked to book · waiting for their yes**. Until the yes: **no payment record, no Pay, no workspace, no shared details (room size, schedule), nothing on their calendar**; the row offers Nudge · Chat · Withdraw only. The yes books them, opens everything — and is the fee event. Booked mode shows a **"Waiting for their yes"** list above Booked; the Budget counts them under "If you book these", never "Booked".
2. **Fee-leak catch at "Add your own".** When the couple types a name or a price, the entry is checked against the quotes THIS couple already received in that category (name match, or price within an **admin-set tolerance** — the prototype's 5 % is a demo value, not a number to ship). A hit shows: *"This looks like Kusina ni Lola's quote · ₱198,000. Bookings made off Setnayan lose the protections — chats, payment records, the date hold — and the supplier skips the booking fee"* with **It's Kusina — book them**. If the couple adds it anyway, the record carries the flag, reads **"Attributed to Setnayan … counts as sourced, flagged for review"**, and the fee attribution is sourced (`booking-fee-gate`: the inquiry source that was stamped at `startServiceInquiry`).
3. **Admin flag list (not on this page — for the admin area, one PR):** a supplier with **N events booked on the couple's side (payments recorded, date held) but no completed booking fee** is flagged: supplier · events · sum of recorded payments · fee owed. N is admin-set. Source tables: `event_vendors` (J7) × `event_vendor_payments` × the fee ledger. This is a list and a threshold — no new mechanism.

**Two locked things this reverses — for the decision log, owner sign-off:** (a) "manual add = booked" (roadmap §5.1 / prod reality) stays true ONLY for suppliers not on Setnayan — the leak check is what stops it being a fee bypass; (b) S19 "pay first, then record" is gone for marketplace suppliers: no record before the yes. **Still open (one word): self-added supplier = `claim` (their claim via QR/link + agree is the handshake; Seda would read "not confirmed by them yet" on the owner's page) or `direct` (as today, no fee anyway).** The prototype draws `direct` + the leak check until told otherwise.

**The Vendor–Event handshake, as it ships (owner: *"connects properly to the Vendor–Event flow up to the handshake to get the booking fee?"*):**
1. **Ask for a quote** = `startServiceInquiry` (SHIPPED): follows the supplier, opens the one thread per (event, supplier), posts the brief, ensures the `event_vendors` row — and this is where the **inquiry source** is stamped, which is what the booking fee reads (`lib/booking-fee-gate.ts`: explore · search · shortlist · … = sourced/billable; `host_manual` · `invite_claim` = import/free). The page's Find list is a sourced surface; "Add your own" is import. The one open owner call (#11): a manual add that matches an existing shop and inquires — sourced or import.
2. **Accept the quote** = `respondToProposal` → RPC `respond_vendor_proposal` (ADAPT): prices the row but does **not** pin it into the build — the prototype's "goes into the build at that price" is two shipped steps (accept, then `setBuildPick`). Accept lives on the proposals page today, not in the thread.
3. **Book** = `finalizeVendor` (ADAPT): marketplace supplier → `lock_request_state='pending'`, **the supplier's yes books them** (couple asks, supplier agrees; behind `isLockHandshakeEnabled()`); self-added supplier → direct lock. It takes no price (price is `updateVendorCosts`) and runs the date-lock, lock-impact, time-slot and reservation-terms confirmations — the prototype's one-field Book sheet must carry those, not skip them.
4. **Pay** = `recordDeposit` (SHIPPED): first payment holds the date, minimum from the accepted quote; later instalments `logScheduledPayment`; proof via `ChosenProofField`. Paid-so-far is the SUM of `event_vendor_payments` — the prototype's free "Paid so far" field has no twin and is dropped.
5. **Cancel booking** (ADAPT): three shipped exits by state — `withdrawVendorLockRequest` (before they agree), `revertVendorToConsidering` (confirmed → considering), `cancelBookingAsHost` (hard delete, only before a downpayment). The prototype's one button must map to the right one per state.
