Two things that change no matter which rows you pick

These are not per-row. They follow from deleting any retired price, so they belong here rather than repeated 43 times.

1 · The supplier suggestion map loses two-thirds of its rows

The admin screen that decides which Setnayan services get suggested to a supplier holds 42 entries. 28 of them point at retired prices and would be removed automatically along with those prices — Live Studio alone accounts for 12.

Suppliers see no difference: that screen only ever shows a suggestion whose service is still on sale, so all 28 already render nothing. The change is on your admin screen, which would go from 42 rows to 14. If you want those suggestions to survive, point them at a service that is still sold before you delete.

2 · A refused purchase gets a vaguer message

Today, if anything ever tried to buy a retired service, checkout refuses it by name: “This service is no longer available.” Once the price row is gone the app no longer recognises the code at all, so the same attempt is refused one step later, by the rule that no sale may proceed without a price — with a generic message instead.

The sale is refused either way. No money can move, and nothing can be bought at a made-up price. What is lost is the polite, specific wording.

3 · A small side-benefit worth knowing

Referral vouchers are built by taking the first 50 services from the price list, in no particular order. The list holds 68, so a voucher today can cover a scattering of retired services and miss live ones. Delete the 43 and the list drops to 25 — every voucher would then cover every live service exactly. No voucher exists yet, so nothing in flight is affected.

What the app’s own delete button would do today — and where it is wrong

The pricing screen already has a “remove for good” button with its own safety check. Run against these 43 rows, that check would say 38 of them are safe to delete. It is wrong in two directions, and both are worth knowing before you press anything:

  • It would let you try to delete the four camera-day prices — and the database would refuse, so you would get a raw technical error instead of a plain reason. The check does not know about the Papic camera-rate settings at all.
  • It correctly stops at the venue photo wall and at the four Setnayan AI rows. Those five it already guards.
  • It weighs whether a price was ever sold. You have told me that does not matter, so I have not used it here. It happens to be zero for all 43 anyway, so dropping it changes no verdict on this page.

The check’s own notes admit the gap in writing: it says the list of “prices the code still reads by name” is a floor, not a ceiling, and that only the Setnayan AI family was ever properly vetted. This page is that missing sweep.

How I looked, and what could still have been missed

The database side

I did not work from a remembered list of tables. I asked the database itself which tables carry a link to the price list — nine of them — and then also counted every loose text column anywhere in the schema that stores a price code without a formal link, because those are the ones a delete would quietly orphan. Twenty-two of the 43 have at least one pointer; twenty-one have none at all.

I also read the price codes out of every stored database routine, every saved view, and every column rule. Ten routines name a retired code; none of them would stop working, because they hold the code as plain text rather than as a link.

The code side — the part a database check cannot do

The dangerous shape is a price code written into the app’s own source as a plain word, used to look the price up. No link exists, so every database check reports the row as free. I hunted for it three ways:

  • Every one of the 43 codes searched across the whole app, with test files and old database scripts separated out so a mention in a test could not be mistaken for a live use.
  • Every place the app reads the price list without asking whether the price is switched on — that filter is what normally hides a retired row, so its absence is the signal.
  • Every named shortcut in the source whose value is one of the 43, followed through to whoever reads that shortcut.

The check that changed three verdicts

Three prices are read by live pages. I nearly reported all three as held. They are not — because in each case the page fetches the price and then only shows it when the service is still on sale, which none of them is. A value that is fetched is not a value that is shown. Had I stopped at “live code reads it”, three rows would have been wrongly locked.

Two independent sweeps, and where they corrected me

After I finished, I had the same 43 codes swept twice more by readers working from the same code but not from my conclusions. They confirmed every verdict and added four things I had not measured — the supplier-suggestion map, the referral voucher cap, the public machine-readable file as a second reader of the Setnayan AI prices, and the “free for every celebration” list that keeps the photo wall, Kwento and Editorial PRO switched on no matter what happens to their price rows. All four are folded in above.

They also raised two worries that the database then settled as false: that receipts might be left naming a raw internal code, and that some of these prices might sit inside a bundle that is still on sale. Neither holds. No purchase record of any kind names a retired price, and all four bundles are switched off.

What a false negative would look like

A price code assembled at run time rather than written out whole — a prefix joined to a number, for example — would not match any search for the full word, and I would have reported it as free. I looked for that pattern and found none, but a search cannot prove the absence of a name it never sees. The same is true of a price code held in a hosting setting rather than in the code or the database; those are not readable from here.

The safest way to use this page: delete the safe rows in small batches rather than all at once, and check the pricing screen and the Papic screen after each batch. Nothing here is time-sensitive.

One thing I could not settle with confidence

The renewal price for Setnayan AI is switched off, but on that row “switched off” does not mean retired — the app’s own notes say it means “not sold on its own”. The only thing that reads it has no callers today, so deleting it would break nothing right now. But it is the price of a thing you are still building. I have locked it rather than call it safe, and that is a judgement, not a measurement.
