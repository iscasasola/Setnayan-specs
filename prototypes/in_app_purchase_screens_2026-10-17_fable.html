In-app purchase, inside the iPhone app

How Papic credits, Live Watch and Event Hub Pro are bought inside the iPhone app with Apple's own sheet, once Apple approves the Paid Apps agreement (owner, 2026-10-08: "if it goes approved, then we will add the apple payment on the app as well before apple check"). The web keeps its apply-then-pay flow (GCash · BDO) untouched. Everything here is the delta on screens that already ship; each caption names what changed and what did not.

Theme
  • Rule 0, measured on origin/main: lib/store-shell.ts hides every paid add-on in the app and refuses every purchase route; apply-pro-sheet.tsx passes no effects and no price in the app (heldOnWeb); choose-plan-sheet.tsx returns null in the app; papic-buy-sheet.tsx goes to /pay. PR #6420 (draft) makes More list only owned services. apps/mobile carries no StoreKit or RevenueCat plugin yet.
  • What this adds: one native "buy" bridge in the Capacitor shell, three buy buttons that already exist pointed at it, one owned/not-owned read that is already the web's (eventOwnsSku over orders), and the honest states around Apple's sheet: success, pending, cancelled, failed, restore.
  • Apple's rules kept: no price of ours, no link to the web, no GCash for a digital item inside the app (3.1.1 / 3.1.3). The supplier booking fee stays on GCash / BDO in the app (3.1.3(e)), as storeShellRefusesPayable already allows.

Under the sheet — the one new bridge

  • One native plugin in apps/mobile (StoreKit 2, via RevenueCat or Capacitor's own purchases plugin — builder's call) exposed to the web as window.SetnayanIAP.buy(productId, eventId) and restore(). The web only ever asks for an owner-named product id; it never knows a price until StoreKit answers.
  • Verification is server-side: App Store Server Notifications v2 → our endpoint → verify the signed transaction → insert the orders row with status paid (the same status the admin stamps on a GCash order) → the existing activation path lights the feature. A refund notification sets refunded → RELINQUISHED_STATUSES already turns it off.
  • Product ids are per SKU: COUPLE_WEBSITE_PRO, LIVE_STUDIO, and one per Papic rung on sale (PAPIC_ONE_500…). Setnayan AI waits (decision 1).
  • Prices stay the admin's on the web and Apple's in the app. Two numbers, one item, never shown side by side.
  • Tests to copy: reads-are-honest.test.ts (a failed read never renders as "not owned"), later-never-takes-the-buy-away.test.ts, the-app-more-lists-only-owned-services.test.ts (PR #6420) — extend, don't invent.

Decisions for the owner

  1. Which items go on IAP first. Recommend: Papic credits (consumable) · Event Hub Pro · Live Watch — the three with a buy button already in a shipped sheet. Setnayan AI second wave: it is a per-user pass with two prices ("₱1,499 now · ₱2,499 later") and a comeback window; Apple's shape for that is a non-renewing subscription, and its price can't change by countdown — it needs its own design. Supplier Pro stays web-only (your ruling).
  2. How Pro is sold in the app. Recommend: only at Apply, as on the web (your 2026-09-30 ruling: no Pro card), one tap in the sheet → Apple's sheet → held ◆ changes applied at once. No Home row, no Pro page in the app.
  3. Apple's product type for Pro and Live Watch. You said non-consumable for Live Watch. Recommend "consumable, applied to the event you're in" for both: Apple lets an Apple ID buy a non-consumable once, ever — a planner with a second event, or a couple's next event, could never buy it again, and Restore would move it to the wrong event. Ownership stays on the event in orders, which is already how the web works; Restore reads our ledger. Alternative: non-consumable, accepting one Pro per Apple ID for life.
  4. Price points and the 15%. Apple sells only at its PHP price points and keeps 15% (Small Business Program, once approved). Recommend: map each item to the Apple point nearest at or above the admin catalogue price, and keep the web price as is — the app never shows the web's, so they need not match. Alternative: raise the web to match, one price everywhere.
  5. How many Papic rungs become Apple products. The web ladder has 17 sizes. Recommend five: 100 · 500 · 1,000 · 5,000 · 10,000 credits — the stepper walks those; fewer products to price, review and keep in step with the admin ladder. Alternative: all 17, mirroring the web exactly.
