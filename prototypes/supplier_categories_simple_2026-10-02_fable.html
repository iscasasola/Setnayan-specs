Event types, religions & supplier categories — one page

Owner, 2026-10-02: “now that we have the proper information needed for each taxonomy, category for suppliers, and we have that taxonomy page where I can add a new leaf category. Can you create the simplest way to manage this page without losing all its features.” and “this covers the event type, the religions, and the different categories that suppliers can be part of.” Three lists today live in six places (the Taxonomy Studio and its two vocab panels, the Aliases page, the per-type Scope / Profile / Onboarding pages, the Ugat Traditions tab). Here they are one page with one dropdown: list on the left, one search, tap a row → one panel on the right, + Add in place. Every link between the lists is edited in one panel and shown read-only in the other, in the same words. “Leaf” never appears — it is a service. “Vendor” never appears — it is a supplier. Counts that need the live database read “—”.

The three biggest simplifications

6 places → 1 page, 1 dropdown
  1. One list per thing, one panel per row. The Studio’s folder rail + tile grid + 3-tab inspector + 2 vocab panels, the Aliases page, the per-type Scope / Profile / Onboarding pages and the Ugat Traditions tab become one left list (Supplier categories · Event types · Religions behind the title dropdown) and one right panel whose sections are always in the same order. Nothing is a separate page any more; collapsed sections carry the rare things (Engine, Combine, Delete).
  2. Every link is edited once. Event type ↔ category: set on the event type (“Categories it shows”), shown read-only on the category. Religion ↔ service: set on the religion (“Services only for this religion”), shown read-only on the service. Religion ↔ event type: set on the religion (“Asked on”), shown on the event type. Today the first link has two editors (tile checkboxes + Scope page) and the third has none.
  3. Choices become one dropdown, status becomes one word. Five view chips → Show ▾. Four event-type buttons across two “grains” (Deactivate · Retire · Show in picker · Un-retire) → Status ▾ with three values. Three faith launch buttons → Status for couples ▾. Promote · Map · Keep private · Reject → Approve as new · Map to ▾ · Decline ▾. Four add paths (prompt, AI card, details form, vocab forms) → one + Add that suggests the place and warns about near matches.

What is drawn but needs a build (not re-laid)

  • Religion ↔ event type has no table today — everything assumes wedding. “Asked on” needs one column (faith_vocab.asked_on_event_types text[], NULL = wedding only) and the trigger that already validates applicable_event_types can validate it.
  • Status ▾ on an event type merges two columns (status + enabled) into three words; the save writes both. Wedding stays locked.
  • Search words on the service panel = the aliases table filtered to that service, plus the waiting rows shown inline. Approve / Reject are the shipped actions.
  • Tagalog name is read today and written by nobody — the panel gives it a writer.
  • “What to expect” is editable for 8 religions today (the table’s CHECK); the panel shows it on all 17 — the CHECK widens.
  • Per-service “Shows for” override exists as a column with no UI; it becomes a dropdown defaulting to “Same as category”.
  • Everything else on this page is a shipped action re-laid: createCanonicalLeaf · mapCategoryRequest · setTileEventTypeOffered · setServiceFaith · createFaithVocab · upsertEventTypeProfile · upsertOnboardingSpec · mergeCanonicalService · deleteTileWithDestination · the attribute-field and refinement mutations.
