A · Saving today, and what a real draft needs

Measured on origin/main

  • Every website-editor save is live the moment it lands. The sub-actions under website/*/actions.ts (updateOurStory, uploadHeroPhoto, updateSiteColors, updateOurPhotos, updateSiteChrome, updateLandingPageVisibility, updateDressCode, updatePhotoMoments, updateSpecialMessage, updateWhatToBring) each update a column on events and revalidatePath; website/widgets/actions.ts writes invitation_widgets rows (is_visible · display_order · mode · config_json); the Save the Date builder's studio/save-the-date/actions.ts writes the std_* columns. There is no draft anywhere for the website — the schema has no draft column on events or invitation_widgets.
  • The Story Maker has a draft in name only. event_editorial.draft_json is the ONE document; saveEditorial writes draft_json and flips status (the audience: draft · event · published · taken_back), stamping published_at, edition_no/volume and freezing room_snapshot on first publish. There is no separate published copy — publishing makes the current draft the live one. Restore-to-last-published is therefore not possible today even there.

The smallest honest design

  • One draft document per event: a new table event_site_drafts (event_id PK · draft_json jsonb · applied_snapshot jsonb · updated_at · updated_by), RLS on the event's hosts (the shipped current_event_ids pattern). draft_json holds only the keys the couple changed; applied_snapshot is what the live columns held when the draft began (this is what Restore compares against and what "N changes" counts). One migration.
  • Apply = one server action that replays draft_json into the real columns through the existing per-field actions (no new write paths; every gate they carry stays), then clears the draft. Restore = delete the draft row. Reset to default = write the prefilled composition into the draft — the same code that writes the page today (invitationWordsDraft, invitationCard, resolveHubLook defaults, the default widget order) — then the couple Applies it, so Reset is itself undoable until applied.
  • Preview reads the draft, guests read the columns. The public page already honours host-only params (?editor=1, ?phase=); the loaders in app/[slug]/_lib/loaders.ts overlay draft_json when the viewer is a host in the editor frame. One change, in one file.
  • Website settings are not part of the draft (address, who can view, guests get, open browsing): a couple who launches expects it to be live now.
  • Reset scope — recommendation: per stage, with per-section reset inside each section's panel. The stage is the unit the switch already gives; a whole-website reset is rarely what anyone means. Reset touches only that stage's look and words and its section visibility/order; it never touches guests, replies, event_schedule_blocks, galleries, orders, event_editorial, the address or visibility. The confirm panel says so, and the destructive button is the form's native reset in this prototype.
  • The Story Maker keeps its own draft_json/publish flow as the Post Event stage's draft; Apply on that stage means its Publish step.

D · One Pro unlock — “try in the draft, pay to apply”

Owner: “okay 2000 it is. i just don't want us to feel cheap … free also has edit but very limited only so they want to pay for that unlock.” Free editing is real but limited to their words and facts (names, date, venue, your words, the reply form, schedule, special message, what to bring, show/hide). Everything that changes how the page looks, moves or what media it shows is Pro. The Pro mark is one quiet glyph, identical everywhere; every one opens the same panel.

Proposed — flagged for the owner (decision 1)

  • With the draft model, a free couple can try a Pro change in the draft — their photo as the hero, a theme, an opening — and see it on their own page in the preview and on all five thumbnails. Only Apply needs Pro. The Apply bar turns into “Apply needs Event Hub Pro · [PRICE] · one-time · all four stages” with one button, Unlock and apply; the panel leads with what they just made (the five thumbnails in their draft state), then one confident price line, then the quiet “Also unlocks” list. Free-only drafts apply normally.
  • Feasible with the design in A, and safe: the draft lives in event_site_drafts, readable only by the event's hosts (RLS); the public page reads the live columns; the preview overlay happens only inside the host-gated editor frame (?editor=1 is already refused for non-hosts). Apply replays the draft through the existing per-field actions, which already carry the Pro gate (eventCoupleWebsiteProActive, the grandfather rule) — so an unpaid Pro key cannot reach a live column even by calling Apply by hand; the action refuses that key and applies the rest. A screenshot of a preview is fine and costs nothing. The live page never shows unpaid Pro.
  • The one real cost: draft media. A free couple trying “their photo” uploads a file. Cap draft media (one hero, a small gallery) and store it under a draft prefix with a TTL (30 days, or until Apply) so unpaid uploads do not accumulate in R2. This softens the 2026-09-24 “uploads are Pro” ruling to “uploads go live with Pro” — say so when deciding.
