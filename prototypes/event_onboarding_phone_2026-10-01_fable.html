The phone detailing of the approved concept (event_onboarding_concept_2026-09-30_fable.html) — nothing new, every card at true size, 390 × 844. One engine, three skins: the same screen draws every card; the event type changes the words, the colours and which cards appear. A wedding (Ana & Miguel), a birthday (Salubong ni Ate) and a wake (Lola Remedios) are shown so the difference is visible, not described. Every card is answered — a quick answer (Not decided yet, I'll add them later) is a real answer, so there is no Skip and no "Later" (owner, 2026-09-30: "we need an answer"). How the same engine changes per type — what the build follows

  • One screen component. Progress bar + "n of N" · one question (≤5 words) · one line (≤12 words) · one control · quick answer · Next. Every frame above is that component; the type profile supplies the words, the colours, the card list and the default answer.
  • Card lists. Wedding 9: names · kind · when · where · photo · look · get in · guests · the list. Birthday 8: whose · when · where · photo · look · get in · guests · the list. Wake 8: remembering · when · where · photograph · look · get in · who should be told · two more. The type step is always names-and-dates; every other signature field stays in Details.
  • Choosing. 2 options → two big buttons (Yes / No, Mine / Someone else, the photo buttons). 3+ → one dropdown (kind · look · how to add · Entry). Never a pill row. The quick answer is either a row in the dropdown (Not decided yet, I'll add them later) or one quiet link under the fields.
  • No Skip, no "Later" button. The decision (amend of 2026-09-30) says every card needs an answer. So there is no "Answer later" control anywhere; the quick answer IS the answer, and one small line says You can change this anytime.
  • Never re-ask. The names/date the flow already has appear pre-filled in the photo preview and the Home; "Mine" pre-fills from the profile; the yearly repeat shows as a chip. Nothing the creation step asked is asked again.
  • How do guests get in? One card, on every type: Will guests reply? Yes / No with the type's default already picked (Yes on all three here) · on No only, Entry ▾ — Personal QR for each guest · One QR for everyone · Both. Nothing else on the card. Changeable later from the Guest list's top dropdown with the same words.
  • Solemn is automatic. The wake reads the profile's register: grey accent, lighter type, Not settled yet, photograph, In loving memory of, Share the news, abuloy, no logo row, no guest-questions row, no countdown, no confetti. No wake-only screen exists — only the words.
  • Two looks, never mixed. Onboarding wears the type's skin; the finish lands on the host's Home in the Setnayan look with the cover and one accent. The event's theme (Velvet · Whimsical · Capiz light) is what guests see, not what the host's tools wear.
  • Finish. One toast (Your Event Hub is ready ✓ / Your notice is ready ✓) on the approved phone Home, plus one quiet Set up · … line that names the answers — so a fresh event never reads as empty.

Questions for the owner (not decided here)

  • Wake default for "Will guests reply?" — the rows name No + one QR only for hangout · date · get-together · simple events, so the wake is drawn as Yes. A wake is often the event people come to unannounced; if the owner prefers No · One QR for everyone as the wake default, it is one line in the profile and the same card.
  • What makes a birthday "formal"? The row says Yes for a formal birthday. Drawn as Yes for every birthday. If a plain party should default to No, the profile needs one signal (a milestone from Turning…, or a "Just a get-together?" answer) — proposal: milestone birthdays (1st · 7th · 18th · 60th …) → Yes; the rest → No + one QR.
  • "Only my list / Anyone, I approve" is no longer on this card (the rows say nothing else on the card). It stays as the Guest list's first-visit question. Confirm that is where it now lives, and that One QR for everyone gets its own "I approve each one" switch on the Guest list, not here.
