# Audit 3 — does every booked path mint a charge?

Source: origin/main (git show / git grep). Read-only. Citations are greppable symbols, never line numbers.

## The finding that frames everything

The code does NOT mint the charge at the handshake. There is exactly ONE minter and ONE call site:

- SQL `public.booking_fee_open_lock_charge(p_event_vendor_id, p_schedule_version)`, called by TS `collectBookingFeeAtLock` (apps/web/lib/booking-fee-lock.server.ts), called ONLY by `runDepositAcknowledgedEffects` (apps/web/lib/deposit-acknowledged-effects.server.ts).
- That fires when the SUPPLIER ACKNOWLEDGES THE COUPLE'S DEPOSIT (`vendorAcknowledgeDeposit` or `confirmVendorPayment`), not when the supplier says yes. Owner ruling 5 of 5 (2026-07-27, reaffirmed 2026-08-03): "vendor will confirm the payment. confirming it will lead them to the booking fee."
- Pinned by `lib/booking-fee-single-trigger.test.ts` (fails on a second caller AND on zero callers). `finalizeVendor`, `lockPackage`, `bookVendorAtChatLock` each carry a "NO FEE HERE ANY MORE" note.
- So "booked (status contracted) with no charge" is the DESIGNED state between the supplier's yes and the deposit acknowledgement. Your stated rule (handshake mints the row) and the owner's ruling 5 (acknowledge mints it) disagree. Decide which one is the rule; the GAP verdicts below are against YOUR rule.
- The real handshake value is `lock_request_state = 'agreed'` (not "accepted"); the supplier's yes is SQL `vendor_agree_to_lock`.
- Booked statuses the minter accepts: contracted, deposit_paid, delivered, complete; anything else returns `skipped: not_contracted`. A row with no `marketplace_vendor_id` returns `skipped: not_verified_vendor`; a package `covered` row returns `skipped: covered_row_no_fee`.
- Attribution (decides waived_import vs billable) is `booking_fee_attribution_for(vendor_profile, event)`: SOURCED only if a `chat_threads` row for the pair has inquiry_source in explore/search/shortlist/first_pick/favorites/auto_build/editorial/influencer. No thread, NULL source, host_manual, invite_claim, degree, website = IMPORT (free). It reads the THREAD, not `event_vendors.source`.
- Order of arms in the minter: import -> waived_import; ordinal<=5 -> waived_free5; fee<=0 -> paid(0); free window active -> waived_promo; else pending (+ `orders` row built by TS).

## Systemic note (affects every GAP row)

An unminted charge FAILS OPEN everywhere. `eventAccessUnlocked` / SQL `vendor_event_fee_gate_stage` treat `kind: 'none'` (no charge) as `unlocked`, and `resolveEventAccessStage` returns 'unlocked' for a booked shop with no charge. Only `pending`, `failed`, `expired` lock. So between the supplier's yes and the deposit ack, and forever on the Locked-QR / admin-settle / forged-status paths, the shop has FULL access and nothing is owed. Under your rule ("no handshake, no record, nothing opens") the safe default would be the opposite. The gate itself is off unless NEXT_PUBLIC_FEE_UNLOCKS_EVENT or `platform_settings.fee_unlocks_event_enforced` is on.

## free5 / promo mechanics (5 lines)

1. free5 is per SHOP LIFETIME, no event-type or year partition: ordinal = count of `booking_fee_ledger` rows with `source='lock'` for that `vendor_profile_id`, ordered by (created_at, ledger_id), frozen once in `booking_fee_ledger.booking_ordinal` / `is_free_booking` (`v_is_free := v_ordinal <= 5` in `booking_fee_open_lock_charge`; TS twin `isFreeBooking` + disclosure `count + 1`).
2. IMPORT ledger rows are `source='lock'` too, so import bookings CONSUME free-5 ordinals even though they never get an ordinal themselves (the import arm returns before the ordinal block). Not pinned by any test I found; owner call whether "first five bookings" means first five of any kind or first five sourced.
3. Waived arms in priority order: import (waived_import) > ordinal<=5 (waived_free5) > fee<=0 (paid, amount 0) > free window (waived_promo) > pending. A booking already free stays waived_free5 (the window never spends a courtesy).
4. Promo window = `platform_settings.booking_fee_free_from` / `booking_fee_free_until` (row id=1), read by SQL `booking_fee_free_window_active()` inside `booking_fee_open_lock_charge` and `booking_fee_open_charge` (fails closed: both NULL = no window; one NULL = open-ended); TS twin `isBookingFeeFreeWindowActive` in lib/booking-fee-disclosure.ts. NOT FOUND any admin UI or app writer of those columns: it is settable only by SQL. A waived_promo booking stays waived on amendment (`promo_noop` in `booking_fee_rederive_lock_fee`). It does not retro-waive an already `pending` charge.
5. Tests pinning it: tests/db/booking-fee-lock.db.test.ts ("free-5 then 5% at the 6th", "idempotent re-lock", "a client the VENDOR brought is never billed", own-link, off-platform, non-contracted skipped), tests/db/a-free-fee-window-waives-the-charge.db.test.ts, lib/a-free-fee-window-fails-closed.test.ts, lib/booking-fee-gate.test.ts (SQL/TS sourced-set mirror), lib/event-access-stage.test.ts (settled set), lib/the-waived-fee-sends-a-receipt.test.ts, tests/db/booking-fee-order-postconditions.db.test.ts, tests/db/the-money-path-end-to-end.db.test.ts, lib/unbilled-fee-repair.test.ts, lib/deposit-acknowledged-effects.test.ts, lib/deposit-acknowledge-fires-from-every-door.test.ts, lib/booking-fee-single-trigger.test.ts, tests/db/lock-handshake-wiring.db.test.ts.

- FLAG-OFF booking fee off (`isBookingFeeEnabled`): `collectBookingFeeAtLock` returns 'disabled' and `maybeCatchUpAcknowledgedDeposits` returns early, so nothing is minted and nothing heals; acks that happen while off must be backfilled by the catch-up after the flag flips (only for suppliers who visit their dashboard).
