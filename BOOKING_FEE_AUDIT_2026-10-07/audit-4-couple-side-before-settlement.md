# Audit 4 · The COUPLE's side before the supplier's charge is settled

Source: origin/main (archive `btn/` for apps/web/app + components; `git show origin/main:` for lib + migrations). Read-only. No line numbers; every anchor is a greppable symbol.

## Headline (the one structural fact)

**NOT FOUND: any couple-facing read of `booking_fee_charges`, `eventAccessUnlocked`, `resolveEventAccessStage`, `resolveEventFeeGate` or `vendor_event_fee_gate_stage`.** `git grep` of those symbols on origin/main hits only `apps/web/app/vendor-dashboard/**`, `lib/vendor-event-fee-access.server.ts`, `lib/event-access-stage.ts` itself, admin pages and SQL. The gate is supplier-side only. Every couple surface below derives "booked" from `event_vendors.status` (CONFIRMED_VENDOR_STATUSES = contracted · deposit_paid · delivered · complete, `lib/events.ts`) and/or `event_vendors.lock_request_state` via `lockRequestStateOf` (`lib/lock-request-state.ts`), plus the deposit markers (`deposit_recorded_at`, `deposit_acknowledged_at`, `deposit_declined_at`). So the "Consults charge?" column is NO on every row; the verdict then turns on whether the surface is at least closed until the supplier's yes.

Chain as built (the charge appears LATE): couple Lock (ask, flag on) -> `vendor_agree_to_lock` writes status=contracted + lock_request_state=agreed (NO charge exists yet) -> couple pays + `recordDeposit` -> supplier `acknowledge_vendor_deposit` -> `runDepositAcknowledgedEffects` -> `collectBookingFeeAtLock` -> `booking_fee_open_lock_charge` (charge minted here, `lib/deposit-acknowledged-effects.server.ts`; `collectBookingFeeAtLock` has exactly one non-test caller) -> supplier settles it. Therefore on main the couple sees "Booked" from the supplier's yes, a full step BEFORE any charge row exists, and "all set" at deposit-confirmed while the charge may still be `pending`.

Second structural fact: `event_vendors_couple_write` is FOR ALL with no column list, and `guard_event_vendor_lock_handshake` only blocks the supplier-answer columns (`lock_agreed_at`, `lock_request_state` in agreed/declined/expired). A couple session can still write `status='contracted'` on any marketplace-linked row (stated in the docblock of `lib/vendor-room-access-rule.ts`; not re-proved against the live DB in this audit). So couple-side "Booked" is a couple-writable fact, not a supplier-confirmed one.

Flag state: `NEXT_PUBLIC_LOCK_HANDSHAKE_ENABLED` = ON in `build-sessions/P0-b-SWITCHES.md` (a dated doc; prod env itself NOT READ here). `NEXT_PUBLIC_FEE_UNLOCKS_EVENT` and `platform_settings.fee_unlocks_event_enforced`: NOT FOUND in that doc; default OFF per `isFeeUnlocksEventEnabled`, so even the supplier-side gate may be inert.

## Direct answers to the three asked items

- `finalizeVendor` off-platform direct lock (row 9): the couple sees Booked (status=contracted, rank 1), the estimated plan, the claim link/QR, and an emailed "Your booking with X is confirmed". NO charge is minted (the only mint site is `runDepositAcknowledgedEffects` -> `collectBookingFeeAtLock`, and it needs a supplier account to acknowledge). Nothing is confirmed TO the supplier (no `booking_confirmed`, no email; they only learn through the claim link, which exposes couple display name and event_date to the link holder). The rows 13 writers (custom wizard pick, own venue, budget supplier fork) do the same with no claim-link copy.
- `recordDeposit` (row 19): yes, it can run before the supplier's yes. It never reads status or lock_request_state. UI exposure: the workspace Payments tab (DepositReservation, unconditional); the chat quote card is gated on status=contracted via `readBookedMoney` (closed on an ask). The DB does not stop it (`guard_event_vendor_deposit_ack` guards only the acknowledgement columns).
- `isLockHandshakeEnabled()` OFF (rows 1, 10, 11, 12): `lockRequestStateOf` returns `none` for every unconfirmed row (no Asked/Waiting anywhere), Lock books instantly, the couple gets the "date is now booked" toast + "confirmed" email, the supplier gets `booking_confirmed` (or nothing, for packages and the wizard). With the flag ON (as P0-b-SWITCHES records) marketplace suppliers are asked first; off-platform suppliers are still direct-locked.

## OPEN list - one-line fix each

1. `lockRequestStateOf` (root of rows 1-7, 16, 26-30): add a third input (the settled-charge fact) and a new state between `requested` and `locked`, e.g. `agreed_unsettled`, and render Booked only for `locked` + settled; every pill/chip/tile above then follows.
2. `recordDeposit` + `raiseChangeOrder` + `logPayment`: refuse unless `lockRequestStateOf(...) === 'locked'` for marketplace rows (read status + lock_request_state in the existing RLS read); also hide `DepositReservation` / pay methods in workspace when `awaitingSupplier`.
3. `readPublishedMethodsForCouple`: return `state:'not_yet'` (no destinations) until the supplier's yes, so the pay sheet cannot show an account number to a couple on an ask.
4. `acquire_schedule_pools` called from `recordDeposit`: gate on `lock_request_state='agreed'` (or call it only from the acknowledge effects) so a couple's deposit stops being ARM 1 of `admitRoomBookings`.
5. `shareMoodBoardWithVendors` + `get_vendor_mood_board`: add `ev.status IN (contracted..complete)` (same list as seat-plan RPC) and the settled-charge check.
6. `emailVendorCallTimes`, `findBookedHost`, `EmceePicks`: filter on CONFIRMED status AND settled; use one shared "booked supplier" reader instead of three definitions.
7. `set_vendor_colour_access`, `request_part_finalization`, PromoteCoordinatorCard: add the settled-charge predicate beside the existing status list.
8. Copy: replace "confirmed" in `payment_info_sent`, `payment_confirmed` ("Your date is locked in") and the workspace rail until the charge is settled; send them from the settle event, not from finalize / deposit-ack.
9. Off-platform direct locks (rows 9, 13): owner decision - either label them "Added" not "Booked", or keep Booked and say plainly it is the couple's own record; stop the "is confirmed" email for them.
10. Flag OFF paths (rows 10, 11, 39): none in prod per P0-b-SWITCHES; if the flag is ever turned off, `booking_confirmed` must not fire from the couple's press.
11. DB: trigger on `event_vendors` so an authenticated session cannot set status in the CONFIRMED list on a marketplace-linked row unless `lock_request_state='agreed'` (couple-writable "Booked" today).
12. `vendorAgreeToLock` / `lock_request_agreed` (row 43): owner to confirm whether the yes itself or the settled charge is the handshake; if the latter, defer the "said yes" notice and the status flip to the settle event.
