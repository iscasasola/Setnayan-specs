Table tagging

The 10-tag cap

Every Papic photo can carry at most 10 tags — both individual and table-fan-out combined. This keeps personal galleries focused on people actually featured.

FAN-OUT ORDER (LOCKED)
1. Sort the table's guests alphabetically by RSVP'd display name
2. Take the first 10 with RSVP status = 'attending'
3. If photo already has N individual tags, only (10 − N) table tags fire
4. Show the operator who was tagged and who was skipped

For the 6 skipped guests, the operator can manually tag them with the Pick action on a different shot of the same scene.

Fan-out rule (locked) Server-side: WITH ranked AS (SELECT g.id, ROW_NUMBER() OVER (ORDER BY g.display_name ASC) AS rn FROM guests g WHERE g.table_id=$1 AND g.rsvp_status='attending') INSERT INTO photo_tags SELECT $photo, id, 'table_qr' FROM ranked WHERE rn <= (10 − existing_tag_count). Wiring Map · Scene 9a

The 10 wiring principles

These are the architectural rules that keep every feature reachable, every action traceable, and every cross-iteration handoff predictable. Apply them across iterations 0000–0019. New iterations earn their place by inheriting these — no bespoke wiring.
PRINCIPLE 01
One canonical entry per actor
Customer = setnayan.com/dashboard/[event_id]/.... Vendor = setnayan.com/dashboard/vendor/.... Operator = Papic native app. Guest = [couple-slug].setnayan.com/me/[guest_token]. Every feature is reachable in ≤ 3 clicks from the actor's home. Buried features are an architecture leak.
PRINCIPLE 02
One canonical key — event_id
Every action that affects an event writes a row carrying event_id. This is the spine. If a record doesn't know what event it belongs to, the wiring is wrong. Cross-iteration queries are joins on event_id, never search-and-hope.
PRINCIPLE 03
One append-only activity log
Table event_activity_log(event_id, actor_id, actor_type, action_type, ref_table, ref_id, payload_json, correlation_id, created_at). Every meaningful action — booking, application, payment, activation, capture, tag, render, unlock — appends one row. The couple sees their timeline; admin sees the audit trail.
PRINCIPLE 04
One apply-then-pay rail
Every paid SKU goes through service_applications → admin confirm → SKU-specific activation hook. No bespoke payment paths. Pro Bundle (₱200), Papic 5-seat (₱2,500), Live Stream Base (₱2,500), Monogram Pack (₱2,000), Broadcast Style Pack (₱3,000), LED Background, AI Highlights — all the same pipe.
PRINCIPLE 05
Activation hooks live in one registry
Table sku_activation_registry(sku_code, handler_fn_name). Admin's "Confirm payment" button calls handler_fn_name by SKU code. New SKUs add one row + one function. No scattered if-else trees. Each hook is idempotent (unique constraint on application_id + slot_index).
PRINCIPLE 06
Event-scoped feature flags
Flags live on the events row: monogram_pack_active, widget_pro_bundle_active, broadcast_style_pack_active. Every consumer (Papic exporter, Live Stream compositor, Reels renderer, gallery chrome) re-checks the flag at asset-generation time — never caches at app start.
PRINCIPLE 07
One chat thread per pair, per event
Couple ↔ vendor gets exactly one chat_threads row per event. All file sharing, video meetings, coordinator-joins anchor here. No DMs outside threads. Permissions resolve through chat_thread_participants only — no event-wide blanket access.
PRINCIPLE 08
Three canonical access tiers
Per asset: owner (full read+write+download original), participant (read+download per role), public (after explicit unlock event). Every gallery query, signed-URL issuance, render-request resolves through this single ladder. No fourth tier.
PRINCIPLE 09
Correlation IDs trace cross-iteration flows
When customer applies for Papic 5-seat, the service_applications row generates a correlation_id. Every derived record — the 5 seats, 287 photos, 14 tags, 1 Personal Reel render — carries the same correlation_id. One query returns the full lineage. See Scene 9b.
PRINCIPLE 10
Every home surface lists every feature
Customer's home lists every customer feature with its status (active / pending / locked / not purchased). Vendor's home lists every vendor feature. Hidden or undiscoverable features are an architecture failure. If a feature exists, the actor home knows about it — even if it's greyed out.
How to apply Every iteration spec opens with a one-pager confirming which of these 10 principles it inherits and which (if any) it extends. If a new iteration needs to break one, that breakage must surface here and in CLAUDE.md's decision log before code begins.
