# Setnayan — SSOT / Hardcode Audit (admin-source vs hardcoded)
Date: 2026-06-18 · Code: origin/main @ 09ec9601 (fresh checkout, 0 behind) · Read-only · 8 listings

## Summary
The app is more admin-driven than not, but unevenly so. Of the 8 listings audited, 2 are genuinely admin-driven end-to-end (event-types and the wedding-faith picker — both read live from DB tables with /admin CRUD; their hardcoded bits are only degraded-mode fallbacks). The other 6 are partially hardcoded, and one — REGIONS/LOCATIONS — has NO canonical source at all (no table, no admin route), surviving as 6+ incompatible hardcoded copies using FOUR different spellings of the same region slugs. The single largest structural problem is that several domains carry TWO parallel vocabularies that never reconcile: vendors pick from a hardcoded 30-item category enum (VENDOR_CATEGORIES) while the marketplace tree it's supposed to feed lives in the admin DB taxonomy (53 tiles); couples express catering/style preferences from a hardcoded list ('Stations') that diverges from the admin-editable vendor facet vocab ('boodle_fight_halal'). On pricing — where the owner rule is explicitly "prices are admin-managed, never hardcode" — the happy-path charge flow IS catalog-authoritative (checkout and Maya billing read the DB and fail closed), but four self-serve surfaces still bill or display from frozen literals: vendor ads, Panood, and two site-editor cards charge/show prices that no admin edit can ever reach. Net: core data (events, guests, taxonomy, charges) is DB-backed and admin-managed; the leakage is concentrated in (a) onboarding preference/vocab lists, (b) regions, (c) a handful of retired-but-still-billing SKU surfaces, and (d) phase-specific nav rosters. None of the live happy-path charge bugs bill real money in prod today, but the region vocab fragmentation and the vendor-category divorce are real correctness hazards that get worse with every admin edit.

## Ranked findings (worst first)
### [MAJOR] Regions / locations (onboarding location step, Top-30 destinations, PSGC place search, vendor region filter, dashboard match-criteria region edit, region-weighted token burn)
- **Verdict:** no_canonical_source
- **Worst site:** apps/web/lib/v2/region-token-burn.ts — BURN_BAND_REGIONS (lines 66-77). This sets the real PESO cost a vendor pays per region (band 1/2/3 = ₱100/₱200/₱300) once the burn economy activates, listing every region slug across all THREE incompatible spellings plus PSGC codes. The file itself admits (lines 44-45) it 'SHOULD migrate to an admin-editable table when activated'; until then a minimum-wage change silently mis-prices vendors with no admin path. The deeper rot: there is no regions table anywhere — onboarding uses one spelling (c-visayas), match-criteria another (central_visayas), PSGC a third (VII), and wedding-cities a fourth (cagayan-valley), so every consumer hand-maintains its own translation map. lib/regions.ts CITY_TO_REGION is also a hand-kept twin of migration 20260620000000's backfill VALUES with nothing enforcing they stay byte-identical, and PH_REGIONS/TOP_DESTINATIONS are dead (their only consumer, the retired Concierge vendor-pick-grid-card.tsx, no longer exists).
- **Fix:** Create one admin-managed table pair as the single source: regions (PSGC code canonical + slug aliases + display label + burn-band) and wedding_destinations (city, region_code, rank, photo_key, nugget). Migrate all 6 hardcoded literals to read through it, collapsing the four spellings into one canonical + alias set, so destinations/ranks/photos/burn-bands become editable without a deploy. Immediate stopgap before that lands: extract the spelling-translation into one shared helper and add the byte-identical CITY_TO_REGION vs migration-backfill check the code comment already mandates.

### [MAJOR] Service & vendor categories (marketplace taxonomy: 10 parents / ~53 tiles / ~200 canonical_service keys)
- **Verdict:** partially_hardcoded
- **Worst site:** apps/web/lib/vendors.ts — VENDOR_CATEGORIES / VendorCategory enum (lines 43-74). This is a SECOND category vocabulary (30 coarse items: venue, photographer, band_dj, officiant, misc…) entirely divorced from the DB taxonomy (service_categories, 53 tiles) that it is supposed to feed. The vendor 'what do you offer' picker selects only from this hardcoded enum, and the save action (vendor-dashboard/services/actions.ts:36) HARD-REJECTS any value not in it — so a category an admin adds at /admin/taxonomy can never become vendor-selectable. Admin edits to the marketplace tree simply never reach vendors. Two further detached copies compound it: dashboard/[eventId]/vendors/categories/page.tsx builds its entire 'add categories' menu from hardcoded WEDDING_FOLDER_ORDER with no getTaxonomy() call, and explore/page.tsx's SEO JSON-LD + ?folder= URL allowlist enumerate parents from constants, so a DB-added/renamed folder is both invisible in structured data and unreachable by direct URL.
- **Fix:** Reconcile the two vocabularies toward the single DB source. Drive the vendor 'what do you offer' picker and its server-side validation from getTaxonomy() (the DB tiles) instead of the VENDOR_CATEGORIES enum; for the transition, generate the coarse enum FROM the DB tiles rather than maintaining it by hand. Replace the hardcoded folder lists in vendors/categories/page.tsx and the explore JSON-LD/?folder= validator with the getTaxonomy() snapshot the visible grid already uses.

### [MAJOR] Hardcoded price literals / SKU price fallbacks (vendor ads, Panood, site-editor cards, Maya billing, vendor subscription, onboarding pricing)
- **Verdict:** partially_hardcoded
- **Worst site:** apps/web/lib/vendor-ads.ts — AD_TIER_OPTIONS[].priceCentavos (line 54 onward). startAdSubscription (vendor-dashboard/marketing/actions.ts:178) writes gross_centavos DIRECTLY from these literals into vendor_ad_subscriptions with no catalog read at all — a live charge path that bypasses the admin catalog entirely. The literals are also stale (₱5,000/500000 here vs the canonical ₱4,999/499900 seed) and all 5 SKUs are already is_active=FALSE/retired, yet an admin retiring them at /admin has zero effect on what the vendor self-serve flow records. Runner-up of equal severity: add-ons/panood/page.tsx PANOOD_SKUS centavos are threaded into ChoosePlanSheet and become the BILLED amount because the V1 codes (panood_daily_broadcast etc.) aren't in platform_retail_catalog_v2, so the checkout resolver returns null and trusts the hardcoded/tamperable client price.
- **Fix:** Route every server action that INSERTs *_centavos through a catalog resolver — extend the existing resolvePaxPricedOrderCentavos/resolveBundleChargeCentavos pattern with a vendor-catalog resolver so vendor-ads and Panood charge from vendor_billing_catalog / platform_retail_catalog_v2 (PANOOD_SYSTEM) instead of literals, and seed the missing Panood rows so the resolver matches. Kill the site-editor's findSku() price display off the V1 tombstone catalog (lib/sku-catalog.ts). Leave the DEMO_MODE-gated PRICING_BOOK and labeled OUT_ANCHORS alone (they never bill in prod).

### [MAJOR] Onboarding preference vocabularies (cuisine / service-style / photo-video look+needs+included; + notification-type registry, patiktok music categories, mood/palette keys)
- **Verdict:** partially_hardcoded
- **Worst site:** apps/web/app/onboarding/wedding/_components/onboarding-shell.tsx — SERVICE_STYLES (line 478). The couple-facing catering vocabulary is a hardcoded ['Plated','Buffet','Family-style','Stations'] set that has DIVERGED from the admin-editable DB-canonical vendor facet vocab (canonical_service_schemas.service_styles = ['plated','buffet','family_style','boodle_fight_halal','intimate_only']): the couple list invented 'Stations' and is missing boodle_fight_halal and intimate_only. So when an admin edits the vendor taxonomy, the couple's preference picker doesn't move, and couple↔vendor match/filter vocab silently disagree — a real matchmaking-quality bug, not cosmetic. CUISINE_OPTS and PV_LOOKS keys are frozen the same way. (Contrast case in the SAME file: REFINEMENTS at lines 500-506 are correctly DB-first via getOnboardingRefinements, proving the right pattern exists.) Behavioral runner-up: lib/notifications.ts NotificationType union + PUSH_ENABLED_TYPES is a hand-maintained mirror of the public.notification_type enum that gates which types fire web-push.
- **Fix:** Make the couple onboarding preference consts read from (or be generated from) the same DB-canonical facet vocab the vendor side uses — canonical_service_schemas facet options + onboarding_refinement_options — exactly as the REFINEMENTS path in the same file already does. That single move fixes the 'Stations' vs 'boodle_fight_halal' divergence and guarantees couple and vendor speak one vocabulary.

### [MINOR] Budget bands + guest roles / role tiers (7-band budget feel ladder; 18-value guest_role enum, 4-tier seating classifier, 13-value moderator role_subtype + permission templates)
- **Verdict:** partially_hardcoded
- **Worst site:** apps/web/app/onboarding/wedding/_components/onboarding-shell.tsx — BUDGET_BANDS (lines 279-287). The per-head median ₱ amounts (essentials ₱2,000 → luxury ₱15,000) live ONLY here, yet they are BEHAVIORAL not cosmetic: they compute events.estimated_budget_centavos (median × pax), which feeds vendor ranking/sorting and bundle-fit logic. No admin can retune the budget compass without a code deploy, which sits in tension with the owner's 'prices are admin-managed' rule (though these are budgeting-guidance amounts, not customer-charged SKU prices). The DB CHECK in migration 20260719000000 even admits the medians are 'locked at the UI layer'. The role vocabularies are lower-risk: guest_role and role_subtype are LEGITIMATELY code-level Postgres enums (adding a value rightly needs a migration); the only hazard there is the TS mirrors (GuestRole union, ROLE_TO_GROUP, PERMISSION_TEMPLATES — which has THREE unsynced copies of its default-grant logic) drifting from the SQL.
- **Fix:** Surface the budget-band per-head medians to a small admin-config table (or fold into the existing /admin/budget-planner) so the budget compass is retunable without a deploy — this is the one item here worth an owner decision given the prices-are-admin-managed rule. For the role enums, leave them in code but add the TS↔SQL exhaustiveness guard (below) so the mirrors can't silently diverge; consolidate PERMISSION_TEMPLATES into one source so its three copies stop drifting.

### [MINOR] Nav/menu labels + icons across the four doorways (customer/vendor/admin dashboards + public marketing site-nav)
- **Verdict:** partially_hardcoded
- **Worst site:** apps/web/lib/customer-menu.ts — buildCustomerMenuTree() Day-of and After phase rosters (lines 137-141 and 147-150). The PLAN-phase nav is fully admin-driven via the nav registry, but the Day-of tabs (Now/Check-in/Seats/Services/Schedule) and After tabs (Home/Review/Editorial/Galleries) hardcode label+icon with NO slotKey and NO NAV_SLOT_DEFAULTS entry — an owner renaming 'Services' or 're-iconing 'Seats' at /admin/menus sees zero effect on the live-event surface. Worse, the existing required guard lint-nav-icon-source MISSES this: it only checks that the chokepoint file mentions navSlots, and customer-bottom-nav.tsx does mention it (for the plan branch), so the un-overlaid day-of/after branches pass CI undetected. The code comment at customer-bottom-nav.tsx:55 openly defers these to 'a follow-up'.
- **Fix:** Add the missing customer.bottom-nav.{now,checkin,seats,services,schedule,review,editorial,galleries} entries to NAV_SLOT_DEFAULTS and apply the navSlots overlay in the day-of/after branches of customer-bottom-nav.tsx, mirroring the 5 plan slots — so all three phases are registry-driven. Then upgrade the guard from file-level mention to per-branch coverage (see guards).

### [MINOR] EVENT-TYPES roster (couple create-event picker, vendor 'event types you serve', marketplace ?event_type= filter, admin taxonomy)
- **Verdict:** db_driven
- **Worst site:** apps/web/app/dashboard/(account)/create-event/_components/event-types.ts — EVENT_TYPES_FALLBACK (lines 39-49). This is genuinely admin-driven: every consumer reads getCreatableEventTypes()/getEventTypeVocab() from public.event_type_vocab (admin CRUD at /admin/event-types; the Postgres enum was deliberately DROPPED). The only hardcoded site is this frozen pre-cutover 9-type roster, used by lib/event-types-db.ts ONLY on a DB read error/empty — a documented degraded-mode safety contract, not a happy-path drift. If an admin adds/renames/retires a type and a later vocab read transiently fails, the pickers silently fall back to the 9-type list instead of the live admin roster.
- **Fix:** Low priority — leave the fallback (it's a legitimate safety net) but add the lint-event-type-source guard + a DB test asserting the dropped enum can never reappear, so the fallback constant can't silently re-fork from the table.

### [MINOR] Wedding faith / ceremony-type picker (onboarding screen 3 + create-event picker — the ~7 selectable faiths)
- **Verdict:** db_driven
- **Worst site:** apps/web/app/onboarding/wedding/actions.ts — commitOnboardingWedding ceremonyType derivation (lines 291-296). This is genuinely admin-driven: the active faith set is read live from public.wedding_type_launch_status, and the gate validates against ALLOWED_CEREMONIES (all 16 registry faiths + civil + mixed), so it does NOT downgrade an active non-catholic faith. The real hazard is a STALE CODE COMMENT (lines 291-293) asserting 'only catholic is an active ceremony_type today' — FALSE since migrations 20260803/06/08 flipped 8 faiths to active. Secondary: the same faith→ceremony_type derivation is triplicated (also ~lines 719, 866) each with a literal 'catholic' fallback, and faith-registry.ts hardcodes jewish defaultSoon:false while the live DB reverted jewish to coming_soon (migration 20261123000000) — so on a DB read failure the offline fallback shows Jewish as selectable when the truth is coming_soon.
- **Fix:** Delete/correct the stale comment, extract the triplicated faith→ceremony_type derivation into one shared helper (so the 'catholic' fallback literal lives in exactly one place), and add lint-faith-gate-default to pin each FAITH_REGISTRY.defaultSoon flag against the seeded launch-status migrations so the offline fallback can never disagree with the admin truth.

## Note
Two framing corrections worth flagging for the owner. (1) The original prompt premise on the faith picker — that it 'downgrades non-catholic faiths to catholic' — is NOT what the shipped code does; the gate accepts all 16 active faiths and only falls back to 'catholic' for a genuinely unknown/empty key. The actual risk there is a stale comment, not a behavioral downgrade. The genuine bleed is the self-serve vendor-ads and Panood flows that insert gross_centavos straight from literals — those are the ones that actually charge from a non-admin source. Priority order for fixes: (1) regions table + spelling collapse (no canonical source, behavioral burn-cost), (2) vendor-category↔taxonomy reconciliation and price-resolver routing for vendor-ads/Panood (both worsen with every admin edit), (3) couple preference vocab → DB, (4) budget-band medians to admin config (owner decision), then the guards.
